## 1. 项目概述

AI Author Forum 是基于 Django + Wagtail 的多期刊内容管理与静态发布平台，覆盖：

- 主站及子期刊管理
- 文章录入、审核、分类与投放
- 版位编排
- 静态站点生成、发布、回滚和审计
- 作者提交与编辑工作台
- 读者身份验证、评论、举报、分享和受保护 PDF 下载
- 中英文后台及公共页面支持

核心业务链路：

```text
导入暂存 -> ArticlePage 草稿/revision -> 审核 -> 正式投放
  -> 冻结构建快照 -> 不可变 manifest -> current 原子激活
```

禁止绕过审核、投放、manifest 校验或审计日志，把草稿、兼容数据或测试数据直接发布到正式前台。

## 3. 技术栈

- Python 3.14
- Django
- Wagtail CMS
- PostgreSQL；读者互动使用独立数据库连接
- Redis：缓存、Celery Broker、结果存储和限流
- Celery：静态发布、读者邮件、评论及 PDF 任务
- Gunicorn
- Nginx
- Docker Compose
- Node.js 22、npm、Webpack、Tailwind/Sass
- Playwright Chromium：静态前台 E2E 和 PDF 渲染
- GitHub Actions：后端质量、前端构建、安全审计、静态 E2E 和 Compose 校验

## 5. 本地开发

```bash
python3.14 -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt
npm ci
python manage.py migrate --database=default
python manage.py migrate --database=interactions
python manage.py seed_navigation
python manage.py seed_roles
python manage.py createsuperuser
python manage.py runserver
```

构建前端：

```bash
npm run build:prod
```

运行静态发布前台时，按 README 中的命令启动静态服务器；不要直接双击 `published/current` 下的 HTML 文件。

## 6. 生产部署

生产 Compose 使用外部 PostgreSQL、独立互动数据库、Redis/Celery 和对象存储，不在生产编排中启动本地数据库或 Redis。

```bash
cp .env.production.example .env.production
# 由接手团队在密钥管理系统或服务器私有文件中填写真实值

docker compose --env-file .env.production \
  -f docker-compose.production.yml build

docker compose --env-file .env.production \
  -f docker-compose.production.yml --profile release run --rm release

docker compose --env-file .env.production \
  -f docker-compose.production.yml up -d --no-build

docker compose --env-file .env.production \
  -f docker-compose.production.yml exec web python manage.py build_static_site
```

发布顺序必须是：构建 -> release 迁移/collectstatic -> 启动或更新服务 -> 健康检查 -> 发布记录。`release` 每个版本只运行一次；Web/Worker 启动时不得执行迁移。

发布完成后至少检查：

- Django `/healthz/`
- Django `/readyz/`
- 静态服务 `/__static_health__/`
- 活动 `manifest`、`release` 和 `current` 目录是否对应本次版本
- Nginx 访问后台、公共静态页面和受保护 PDF 的结果
- 数据库迁移状态、Celery 队列和错误日志

## 8. 账号与权限

平台标准角色：

- 超级管理员：账号、配置、投放、静态发布和回滚；不能执行文章终审。
- 主编辑：被任命期刊的团队、内容、初审、终审和投放。
- 常务副编辑：被任命期刊的日常维护、分派、初审和投放；不能终审。
- 副编辑：被任命期刊的初审及分配的维护职责；不能终审。

业务范围由 `JournalEditorAssignment` 和统一权限 service 决定，不得仅通过直接修改 Wagtail Group 成员关系授予期刊业务权限。

高风险动作必须写入不可修改、不可删除的 `AuditLog`，包括发布、失败、重试、回滚、导入和权限变更。

## 9. 数据、备份与恢复

接手团队必须补齐并书面确认以下内容：

- PostgreSQL 主库和互动库的备份周期、保留周期及恢复演练记录
- Redis 是否持久化，以及缓存/队列丢失时的处理方式
- 媒体、静态发布目录和受保护 PDF 的对象存储备份策略
- 数据库迁移前后的备份点
- 静态发布 release 与 manifest 的保留数量
- 管理员、编辑和读者个人数据的访问审计与脱敏要求

回滚只能切换到已验证且完整的历史 manifest，不得将数据库静默恢复到任意历史状态。数据库恢复和代码回滚必须分别评估并记录。

## 11. 当前运行环境交接事实

交接核查时服务器上观察到：

- `ai-author-forum-test`：10 个容器运行，测试环境完整。
- `ai-author-forum-current-production`：5 个容器登记运行，但 Web 容器持续重启，Nginx 容器未启动；不应视为可用生产环境。
- 当前服务器 Nginx 的公网代理目标为 `127.0.0.1:18080`，对应测试环境入口。
- 生产容器和测试容器使用了同一套 Compose 项目配置路径的迹象，接手团队必须先梳理项目目录、Compose project name、卷和环境文件，再进行任何生产操作。
- 服务器上另有 `company-reimbursement` 和 `resume-cli` 项目；它们不属于本项目交接范围。

以上是交接时的现场状态，不代表新的生产承诺。接手团队应在正式接管后重新巡检并形成带时间、版本和命令输出的发布记录。
