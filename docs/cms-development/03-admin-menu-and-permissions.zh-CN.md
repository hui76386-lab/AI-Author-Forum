# 03 后台菜单与权限

> 当前已运行角色基线仍以本文为准。2026-08-04 起，下一阶段统一采用 [08 账号、子期刊编辑角色与审核开发任务书](./08-account-and-editorial-access-development-spec.zh-CN.md) 的简化模型：平台超级管理员、子期刊主编辑、常务副编辑和副编辑。在新权限通过迁移和测试验收前，不得提前移除本文现有权限护栏。

## 1. 目标后台结构

后台按业务任务而不是按 Django app 平铺。推荐结构：

```text
内容
  文章
    所有文章
    待审核
    投放同步异常
  子期刊
    子期刊资料
    批量导入
    栏目管理
    栏目变更记录

投放与版位
  人工投放
  系统栏目投放（只读）
  版位管理
  投放同步异常

导航与页面
  主站导航
  子期刊导航
  默认子期刊模板
  内容栏目配置

发布
  静态发布中心
  失败重试
  回滚

系统
  站点配置
  角色权限
  审计日志
```

## 2. 菜单收口原则

当前存在以下职责重叠，整改时应只保留一个主入口：

| 当前重叠 | 统一方案 |
| --- | --- |
| “文章管理”与“所有文章” | “文章”作为主入口，“所有文章”作为列表视图 |
| “文章审核”与自定义审核页 | “待审核”统一进入同一审核服务和权限检查 |
| “投放管理”与“系统栏目投放” | “人工投放”和“系统栏目投放（只读）”明确分层 |
| “投放管理”与“版位管理” | 投放是关系，版位是位置；分成两个子入口 |
| “静态发布”与 `Static publishing` | 只保留“静态发布中心”，英文兼容入口退役 |
| “栏目与导航”“栏目管理” | 子期刊下管理栏目，导航与页面下管理导航基线 |

已定义但未最终注册的 `NavigationGroupViewSet` 和 `ContentColumnConfigViewSet`，在注册前必须先确定它们是否为正式入口；如果只是服务层或兼容层，不应继续出现在代码中作为“半可用 ViewSet”。

## 3. 角色与用户组

下一阶段业务角色基线（V2 开启后）：

| 角色 | 应有能力 | 不应有的能力 |
| --- | --- | --- |
| 超级管理员 | 全平台后台、账号、子期刊、角色、投放、静态构建、激活、重试和回滚 | 不得绕过主编辑终审服务；不得多人共用账号 |
| 主编辑 | 本刊全部文章、编辑团队、初审、终审、本刊期次和本刊投放 | 其他期刊、平台账号和平台配置 |
| 常务副编辑 | 本刊日常统筹、初审、编辑维护、本刊期次和本刊投放 | 终审、账号管理、其他期刊和平台配置 |
| 副编辑 | 本刊初审和被分配的文章/期刊资料维护职责 | 终审、账号管理、其他期刊和平台配置 |

`项目总负责人`、`内容管理员`、`审核人员`、`站点运营`、`发布管理员` 和 `只读人员` 只作为旧系统迁移来源，不作为 V2 目标角色。

迁移前兼容状态仍可能存在 `Content Reviewers` 和“审核人员”旧组；它们只用于旧版本回退和迁移报告。V2 开启后不得继续以旧组作为业务授权来源，必须由 08 号任务书定义的 `ArticleInitialReviewTask`、`ArticleFinalReviewTask` 和 `JournalEditorAssignment` 判定初审/终审。

## 4. 权限设计要求

每个入口至少定义：

- 菜单可见权限；
- 列表查看权限；
- 新增/编辑/删除权限；
- 审核或发布动作权限；
- 跨站点/跨期刊范围；
- 审计日志要求；
- 失败后的重试或回滚权限。

不能仅靠菜单隐藏实现安全控制。菜单 hook、ViewSet、service 和 management command 都必须重复做对象级权限/角色检查。

## 5. 高风险动作

以下动作必须有明确 codename、确认页、操作者和审计记录：

- 批量导入/覆盖；
- 审核通过或驳回；
- 文章投放、取消投放、覆盖系统投放；
- 静态构建和 current 激活；
- 失败重试；
- 回滚；
- 修改核心导航、站点配置和发布目录。

审计至少记录：操作者、时间、动作、对象类型、对象 id、旧值摘要、新值摘要、request id、release id、结果和错误信息。

## 6. 权限验收场景

- V2 副编辑和常务副编辑登录后只能看到被分配子期刊的初审和维护入口；
- V2 主编辑能处理本刊待初审和待终审，但不能管理平台账号；
- V2 超级管理员能维护全平台，但不能通过全局权限绕过主编辑终审；
- 只读人员能查看审计记录，但不能从列表动作按钮触发写操作；
- 旧角色迁移完成后，项目总负责人不再作为 V2 系统角色；
- 命令行导入、发布、回滚也必须使用和后台一致的权限/审计策略，不因脱离 HTTP 请求而绕过控制。

## 7. 2026-07-23 审核组与权限收口

- V2 Workflow 顺序为初审任务 -> 终审任务；旧英文 `Content Reviewers` 和“审核人员”组不再授予新审核动作。
- 角色迁移会将旧用户按人工映射转换为主编辑、常务副编辑或副编辑及具体子期刊范围，不能自动扩展为全刊权限。
- 审核、投放、静态发布、重试和回滚仍由 Django/Wagtail permission 在服务或视图入口强制校验；菜单隐藏只改善可见性，不能替代授权判断。
- V2 超级管理员保留全局维护能力，但终审、发布、导入、重试、回滚等高风险动作仍必须写入 `AuditLog`；审计写入失败时动作不得被报告为成功。

该收口只落实 07 文档中的保守权限基线，不代表 D-01～D-10 已形成产品决策。
