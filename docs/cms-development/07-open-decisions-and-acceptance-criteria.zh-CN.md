# 07 待确认需求与验收标准

## 1. 必须由产品/项目负责人确认的决策

以下问题不能仅靠工程师猜测。未确认前，代码应采用保守策略：不自动发布、不覆盖旧数据、不立即下线旧 current，并留下待处理状态。

| 编号 | 问题 | 默认保守行为 |
| --- | --- | --- |
| D-01 | 导入后是否自动创建 `ArticlePage` 草稿并提交审核？ | 自动创建草稿，但不自动通过审核、不自动发布 |
| D-02 | 已发布文章修改后是否必须重新审核？ | 必须重新审核，旧 current 保持不变 |
| D-03 | 驳回已上线文章是否立即下线？ | 不立即删除旧 current，进入人工下线/回滚决策 |
| D-04 | 审核通过是否自动创建系统投放？ | 不自动创建；必须有明确投放规则或人工投放 |
| D-05 | 人工投放与系统投放谁优先？ | 人工投放覆盖系统投放，但必须显示覆盖关系 |
| D-06 | 静态构建部分失败时是否允许发布成功页面？ | 默认不激活新 manifest，保留旧 current |
| D-07 | 回滚是否同步恢复数据库业务状态？ | 默认只切换静态 manifest，并标记数据库差异待处理 |
| D-08 | 期刊 slug 是否允许修改？ | 默认不允许直接修改，必须提供迁移/重定向方案 |
| D-09 | `related_journals` 可投放到哪些页面？ | 默认只允许明确配置的推荐位 |
| D-10 | “系统栏目投放”是否允许人工编辑？ | 默认只读，规则由栏目配置生成 |

### 1.1 2026-08-04 账号与编辑权限开发基线

以下新增事项已由 [08 账号、角色与编辑权限开发任务书](./08-account-and-editorial-access-development-spec.zh-CN.md) 固化为开发基线，不改变 D-01～D-10 的既有状态：

| 编号 | 已确定事项 |
| --- | --- |
| D-11 | 平台级角色只保留超级管理员；“项目总负责人”不再作为目标系统角色 |
| D-12 | 每个子期刊配置一名主编辑、一名常务副编辑和多名副编辑，角色按子期刊隔离 |
| D-13 | 副编辑和常务副编辑负责初审，主编辑负责终审；本阶段不建设外部审稿人流程 |

具体角色职责、模型、任务依赖、迁移、测试和切换标准均以 08 文档为准。

## 2. 模块验收标准

### 2.1 导入

- [ ] 可预览错误，不污染正式文章；
- [ ] 每行有唯一导入结果和错误原因；
- [ ] 重复导入幂等，不静默覆盖已发布内容；
- [ ] 导入后能看到正式 `ArticlePage` 草稿；
- [ ] 导入命令不能绕过审核和投放直接发布；
- [ ] 图片匹配、缺失和引用保护有结果展示；
- [ ] 导入动作有审计日志。

### 2.2 文章审核

- [ ] `draft`、`submitted`、`pending_final`、`approved`、`rejected` 状态可追踪；
- [ ] Workflow 固定为初审和终审两个任务，并与自定义页面使用同一业务 service；
- [ ] 初审只允许本刊有效副编辑、常务副编辑或主编辑，未分配文章先执行原子认领；
- [ ] 终审只允许本刊有效主编辑，超级管理员和直接 Django permission 均不能旁路；
- [ ] 退回、拒绝和超级管理员应急初审的意见必填规则明确；
- [ ] 终审通过记录准确的 `approved_version`，并存在同 revision 的初审和终审不可变记录；
- [ ] 过期 revision、错误 expected state 和并发重复 request 返回冲突且不重复改变状态；
- [ ] 正文或作者声明变更后回到草稿并重新经历两级审核；
- [ ] 审核与审计在同一事务，审计失败时业务动作回滚。

### 2.3 投放与版位

- [ ] 只能投放已审核正式文章；
- [ ] 目标期刊/栏目/slot 必须存在且有效；
- [ ] 同一文章、同一 slot、同一时间区间的重复规则明确；
- [ ] 人工和系统投放覆盖关系可解释；
- [ ] 排序、置顶、生效时间在静态构建中一致；
- [ ] 同步失败可见、可重试、可审计。

### 2.4 静态发布

- [ ] 构建输入是冻结快照；
- [ ] 每页有成功/失败结果；
- [ ] 生成不可变 manifest；
- [ ] 新版本失败不影响旧 current；
- [ ] current 切换是原子动作；
- [ ] 只有有效超级管理员可以构建、激活、重试和回滚；
- [ ] 前台不依赖文章数据库实时查询；
- [ ] 回滚后页面、manifest、审计记录一致。

### 2.5 后台与权限

- [ ] 角色登录后菜单不同；
- [ ] 菜单隐藏不是唯一安全措施；
- [ ] 业务角色只有超级管理员、主编辑、常务副编辑和副编辑；技术组不提供业务授权；
- [ ] 超级管理员拥有平台维护和全部账号管理权限；
- [ ] 主编辑、常务副编辑和副编辑只能访问被分配的子期刊；
- [ ] 副编辑初审、主编辑终审的边界不能绕过；
- [ ] 所有高风险动作有确认和审计；
- [ ] 无重复或无法解释的后台入口。

## 3. 发布前必须执行

```powershell
cd "E:\AI Author Forum\news-template"
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
ruff check ai_author_forum tests scripts
black --check ai_author_forum tests scripts
isort --check-only ai_author_forum tests scripts
pytest
npm run build:prod
npm run test:e2e
```

如果本地环境无法执行 Docker，则必须在发布记录中明确“未完成 PostgreSQL/Redis/Celery/Nginx 联合验收”，不能把本地 SQLite 结果表述为生产验收通过。

## 4. 文档维护规则

- 变更模型：更新 01、04；
- 变更导入/审核/投放/发布流程：更新 02；
- 变更后台菜单或权限：更新 03；
- 变更静态目录、manifest、Nginx 或运维命令：更新 05；
- 修复冲突或新增风险：更新 06；
- 产品决策完成：更新 07 并补充决策日期、决策人和影响范围。
